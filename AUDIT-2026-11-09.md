## 9. Third pass — browser pairing (2.3.0)

Ported the *idea* from NEXORA-MD's `src/web/pairWeb.js`, not its code: NEXORA is an
ESM fleet-of-sessions bot with an approval queue and an express/helmet/rate-limit
stack; Akoya is one CommonJS socket. What was kept is the lifecycle that makes it
work, what was rebuilt around Akoya's shape:

**Kept (the ideology)**
- The visitor triggers the code; nothing is requested at boot.
- The code is rendered only to the holder of a one-time polling token, never sent to
  WhatsApp or Telegram, never written to the terminal.
- Lifecycle phases `starting → code → linked`, plus `failed`, `expired_code`, `busy`.
- A socket that closes *after* the code is accepted is resumed (creds.registered),
  not torn down: that is the "stuck on logging in" bug.
- A socket that drops *before* the code is entered re-issues a fresh code, twice,
  and the page says the old one is dead.
- Start attempts are rate limited (3 / IP / 10 min), polling too (150 / 10 min), and
  tokens expire after 15 minutes.

**Rebuilt for this bot**
- Zero new dependencies: `node:http` + `crypto`. `npm install` still resolves 469
  packages, no express/helmet/express-rate-limit.
- The page is fully self-contained (no Google Fonts, no CDN), so it renders on a VPS
  with no outbound access. CSP `default-src 'none'`, frame-deny, no-referrer.
- No approval queue: this bot is single-tenant, so there is nobody to approve a
  stranger. Instead `global.webPair.key` optionally gates the code request.
- The same server keeps `/health` (`{ ok, phase, linked, uptimeSeconds }`) after
  linking, which is what hosting panels and uptime checks actually want.
- Terminal pairing is kept as a fallback: web disabled, or the port fails to bind and
  `process.stdin.isTTY` is true.
- A non-TTY host no longer dies on the readline prompt: that was the old behaviour
  (`ERR_USE_AFTER_CLOSE`), and it is why this feature is worth having.

**Bug found while wiring it:** `global.pair = "AKOYAMD"` was 7 characters.
`requestPairingCode()` only accepts a custom code of exactly 8 (`A-Z`, `0-9`), so the
old code path either failed or fell back unpredictably. `global.pair` is now empty
(WhatsApp generates the code), a custom value is only passed when it is exactly 8
characters, and the bot warns at boot when it is not.

Files: new `source/webpair.js`; `index.js` gains the state bridge, the pairing block
and the `/health` boot; `settings.js` gains the `global.webPair` block.

Verified: 20/20 API assertions against a stub code requester (page, CSP, phone
normalisation, token gating, rotation, rotation budget, linked state, health, rate
limits, access key, disabled mode), rendered page has balanced markup and a
`node --check`-clean client script with zero external requests, and a real boot
serves `/pair` + `/health` on port 3000 while the socket connects. A real WhatsApp
code has not been requested, because that needs a phone in hand.

## 10. Fly.io target (2.3.1)

The pairing page was built for a local port; it now ships as a container that runs on
Fly without edits.

- `Dockerfile` — `node:22-bookworm-slim`, `npm ci --omit=dev` before the code copy so
  changes do not reinstall 469 packages, `EXPOSE 8080`, entrypoint `scripts/fly-start.sh`.
- `scripts/fly-start.sh` — the important part. If `/data` is mounted it seeds
  `library/database` from the image on first boot, then symlinks `session` and
  `library/database` onto the volume and execs the bot. Without this, every
  `fly deploy` would silently log the bot out and reset users/groups/premium.
- `fly.toml` — one machine, `auto_stop_machines = false`, `min_machines_running = 1`
  (a WhatsApp socket must never scale to zero or run twice), `internal_port 8080`,
  `force_https`, `/health` check with a 25s grace period, volume `akoya_data` at
  `/data`, 1gb shared-cpu-1x.
- `settings.js` — `PORT`, `WEB_PAIR_ENABLED`, `WEB_PAIR_PORT`, `WEB_PAIR_HOST` and
  `WEB_PAIR_KEY` are read from the environment, so Fly secrets gate the page without
  editing files.
- `.dockerignore` keeps `node_modules` and any local `session` out of the image.

Verified locally (no Docker daemon in this sandbox): `fly.toml` parses (tomllib),
`sh -n` on the entrypoint, and the entrypoint run against a fresh fake volume seeds
`owner.json` with `233533416608@s.whatsapp.net` and creates both symlinks. A boot with
`PORT=8080 WEB_PAIR_KEY=flytest` served `/pair` and `/health` on 8080, reported
`keyRequired: true`, rejected a keyless start with 401 and accepted the keyed one.

Caveat worth stating: `requestPairingCode` happily returns a code for numbers that are
not real, so a public `/pair` before linking is a small abuse surface. Hence the
documented `fly secrets set WEB_PAIR_KEY=...` step, and the 3-per-10-minutes limit.

## 12. Pairing codes: why it showed a random one, and why a failure left the bot dead (2.3.3)

Two separate faults, both confirmed from the live logs rather than guessed.

**The random code.** `global.pair` was empty, so `requestPairingCode()` was called
with no custom code and WhatsApp generated its own. The owner wanted "akoyamd", which
is 7 characters, and WhatsApp only accepts exactly 8 (A-Z, 0-9). The old
`customPairCode()` threw away anything that was not exactly 8 and quietly said
nothing, which is precisely how a wish turns into a random code. It now pads a short
code with 1s: `akoyamd` ships as **AKOYAMD1**, and the console states the effective
code at boot so there is no room for a wrong assumption.

**The failure.** The log is unambiguous: a code was issued at 22:12:01 and at 22:12:17
the socket closed with 401. Sixteen seconds is far too fast to be expiry, so the phone
had typed "akoyamd" while the page showed a different code, and WhatsApp rejected it.
Then two bugs compounded it:

1. `markDisconnected(401)` treated *every* 401 as "this session was logged out", so a
   rejected pairing attempt wiped the number and told the owner to restart the bot.
2. `handleStatus()` checked `!snap.ready` before the `failed` phase. A refused attempt
   had already closed the socket, so the page kept reporting `starting` and spun on
   "Talking to WhatsApp…" until the phone gave up with "Couldn't link device".

Fixes: a 401 is now classified by whether the device was ever paired. An unpaired 401
is a rejected attempt: the number is kept, the message says the code was wrong or
expired, and `index.js` reopens the socket (bounded at 5 attempts) so the page can
hand out a fresh code instead of the bot staying dead until a restart. A paired 401
means the device was removed, so the stored session is deleted and the bot goes back
to pairing on its own. Status is now reported as `failed` regardless of socket state,
the retry limit went from 3 to 8 starts per 10 minutes so a typo does not lock the
page, and the page shows the exact code it will issue before the button is pressed.

Verified: `customCode: "AKOYAMD1"` in `/pair/api/info`, boot log
`Custom pairing code: AKOYAMD1 (from "akoyamd" — WhatsApp requires exactly 8 characters)`,
`markDisconnected(401, {paired:false})` leaves the phone intact with the "code was not
accepted" message while `{paired:true}` produces the removed-device message, and the
page renders the hint element.

### Follow-up: the 401 at boot

The first deploy of this fix still booted into `phase: failed`, five refused attempts in
a row. The cause was the session folder left on the volume by the abandoned attempt:
credentials with `registered: false`. WhatsApp rejects those the moment they are
presented, which looks exactly like a refused code and cannot be recovered. Unregistered
credentials can never become registered later, so `startingBot()` now discards them
before the handshake (`discardUnpairedSession`) and logs it. The reopen loop also no
longer spins when no pairing was actually in flight, because reopening cannot fix a bad
stored handshake.

Verified locally with a planted `{"registered":false}` creds file: boot logs
`Discarded an unfinished pairing session`, `/pair/api/info` reports `starting`, and no
401 appears. Then a real `POST /pair/api/start` for a test number returned
`{"phase":"code","code":"AKOYAMD1"}`, so the brand code is what WhatsApp issues now.

## 15. Session survival and the styling pass (2.3.6)

### The redeploy bug

The volume was fine: `fly machine exec ... ls /data/session` showed `creds.json`
persisting across deploys. The file itself was the problem — `"registered": false`.
Boot ran `discardUnpairedSession()`, decided the handshake was unfinished and deleted
the folder. So every deploy (and every reconnect) threw away a session and asked for a
new pairing code. Repeated pairing is exactly the behaviour that gets a number flagged.

Fixed by making the disk authoritative and nothing disposable:

| Rule | Why |
| --- | --- |
| `prepareSession()` reuses creds when `registered === true`, `me.id` exists, or a `.linked` marker exists | a session can be valid without the flag having been flushed |
| an unfinished handshake is renamed to `session.unpaired-<ts>`, never deleted | nothing is ever lost silently; the newest 5 are kept, older ones pruned |
| `markSessionLinked()` writes `registered: true` and `.linked` the moment the socket opens | the flag lands on disk instead of living only in memory |
| every creds write also lands in `creds.json.bak` via tmp + fsync + rename | a SIGKILL mid-write cannot cost the session |
| a corrupt `creds.json` is restored from the backup at boot | covers the redeploy that lands mid-write |
| SIGINT/SIGTERM flush the session before exit | Fly allows 20s before SIGKILL |
| `fly-start.sh` rescues creds from a container that booted without the volume | protects against a mount failure wiping a working pairing |

`GET /health` now returns a `session` block (`registered`, `backup`, `linkedAt`, `jid`,
`credsUpdatedSecondsAgo`), so a deploy can be verified from outside without SSH.

Pairing-side ban-bait reduction: `onSocketReady()` only rotates a code while somebody has
polled the page in the last two minutes (`state.lastPollAt`); otherwise it drops to idle
and stops spending codes on a reconnect nobody is watching. Unpaired sockets back off to
15s → 5min instead of hammering every 2s.

Tests: `npm run test:session` (6 cases: first boot, linked reuse, marker reuse,
quarantine, backup restore, freeze-on-open). All pass.

### Styling

The earlier translation flattened the Unicode fonts and, worse, styled code inside
`${...}`: `${total}` became `${𝗍𝗈𝗍𝖺𝗅}`, which is a valid identifier and therefore a
silent runtime `ReferenceError`. Repaired 6 placeholders and rewrote the transfer so it
copies style word by word from the original literal (index-aligned when the word counts
match, proportional otherwise) and never touches a `${...}` hole. A literal is now
translated by rebuilding the file segment by segment instead of splicing by offset —
that is what corrupted `case.js` mid-way.

## 19. Games going unanswered (2.4.2)

`.menu` had been fixed, then game commands stopped answering while `.mute` still logged.
The log buffer ended before any game command: nothing reached the `[CMD]` line. The
handler awaits `client.groupMetadata(chat)` before it even parses the body, and an
unbounded query there swallows the message with no trace.

Every incoming message now logs one `[IN] <dm|group> <chat> <kind> <body>` line before
anything else can fail, and the group lookup races an 8 s timeout so a slow query degrades
to a cached or empty metadata instead of eating the command. `.mute` also threw in a
direct chat on an unregistered group entry; it now replies that mute is group-only.

## 23. Pairing alerts: the build reports itself (2.6.1)

The bot could pair silently. If a copy of this build were deployed somewhere else and
someone linked a number to it, nothing here would ever know — which makes advertising
a guess. So pairing now reports itself:

- `source/pairtrack.js` keeps the funnel (page opens, codes requested, pairings, wrong
  codes, refusals, removals) in `library/database/pairs.json`, on the volume, capped at
  400 events and 90 daily buckets, written debounced and again on `exit` so a deploy
  does not drop the newest events.
- One note per genuine pairing goes to `global.owner`. `registered` flipping false ->
  true in `markSessionLinked` is the only honest definition of a new pairing, so
  reconnects and redeploys stay quiet. A pairing socket cannot send, so notes raised
  before the session opens are queued and flushed on `open`; a single in-flight drain
  prevents a queued note being delivered twice.
- Also announced: a number this build has never seen asking for a code (the earliest
  proof an advert worked), a device removed on the phone (`DisconnectReason.loggedOut`
  while paired), and a jadibot a user pairs (`entry.pendingPairing`, set only when a
  code was issued in this process, so a restore does not re-announce).
- Numbers are masked unless they are the owner's. Geo is a best-effort `ipapi.co`
  lookup with a 2.5s timeout that resolves to nothing on failure — the note is never
  delayed by it.
- `clientIp()` now reads `fly-client-ip` before the socket address. Behind Fly the
  socket is the proxy, so every visitor previously shared one address: that weakened
  the rate limits as well as the geo.
- The pairing page posts its `?utm_source` / `utm_medium` / `utm_campaign` / referrer
  with the number, so a pairing can be attributed to the campaign that produced it.
- `.pairs` (owner only) prints the report; `GET /pair/api/stats?key=` serves the same
  numbers as JSON, keyed by `PAIR_STATS_KEY` or `WEB_PAIR_KEY`, and answers 404 when
  neither is set. `global.pairAlerts = { enabled: false }` keeps counting and stops
  the notes.

Verified: a simulated visit, code request and link through the real HTTP server records
`{visits:1, attempts:1, linked:1}`, the two notes render correctly and stay queued while
the socket reports unregistered, the wrong key gets 401, the right key gets the JSON,
the report survives a process restart, and `npm run check:menu` still resolves all 241
advertised commands.
